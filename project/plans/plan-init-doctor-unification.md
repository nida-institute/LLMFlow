## 1. What I understand the goal to be

`sp init --update` and `sp doctor` are to be synonyms with one implementation behind them.
Today they are two implementations that disagree, and the disagreement destroyed authored
content in a consumer repo (§2). The Captain's ruling is that the file catalog is the sole
authority on what `sp` owns, that the `<!-- Generated by sp init -->` ownership *check* is
an old design and goes, and that `sp init --update` refreshes the hello-world example when
present and then delegates.

Correctness has two halves and both are required: the fix that reaches a project must keep
reaching it, and a project's own authored work must not be overwritten without its policy
saying so.

## 2. What prompted it — the discourse-flow loss

`sp doctor`, run in `nida-institute/discourse-flow`, overwrote two files that
`sp init --update` would have left alone.

| file | before | after |
|---|---|---|
| `docs/ai-context/index.md` | 203-line hand-authored navigation map | packaged `AI_INDEX_DOC` |
| `.github/copilot-instructions.md` | 72 lines of project specifics | 3-line pointer (`COPILOT_INSTRUCTIONS_DOC`) |

Unique content in the index that existed nowhere else: `project/HANDOFF.md` marked *"First,
every session"*, and pointers to the two #75 design documents carrying their warnings —
`per-verse-representation-defect-design.md` with *"Read its §0, two ratified decisions were
reversed"* and `book-discourse-flow-boundary-granularity-design.md`. The rest of what went
(`docs/field-reference.md`, `docs/translation-usj-reform.md`, `docs/OVERVIEW.md`, the
pipeline/plugin/prompt/schema directory pointers) also lives in that repo's committed
`AGENTS.md` "Where to find things" table. From `.github/copilot-instructions.md`: the
pipeline name, the `--var book=` values, the `--rewind-to prepare_synthesis_input` recipe,
the `output/intermediate/` warning, and the AI-authority-boundaries section.

**Both were working-tree modifications, so nothing is lost** — recoverable in that repo
with `git restore docs/ai-context/index.md .github/copilot-instructions.md`. That recovery
is the Captain's to run; this repository's plan does not carry it out.

**The mechanism.** Two commands answered "does sp own this file's content?" differently:

- `sp init --update` guards every write with `_is_generated()` (`cli_utils.py:590`), which
  requires the first line to be exactly `<!-- Generated by sp init -->`
  (`cli_utils.py:587`).
- `sp doctor` ignores that marker by design (`doctor.py:11-13`: *"not from sniffing
  `<!-- Generated by sp init -->`. That marker's text had already drifted in shipped
  code"*) and reads only the catalog's `policy` field. `docs/ai-context/index.md` is
  `policy: generated` (`data/file-catalog.yaml:81-86`), so `_diverged()` → `_restore()`
  rewrites the whole file (`doctor.py:198-202`).

The two overwritten files are precisely the ones the marker protected:

```
index.md   <!-- Project-specific AI context for discourse-flow. Hand-authored (replaces llmflow-init boilerplate). -->
copilot    <!-- Generated by llmflow init -->        ← the old, drifted marker
```

Both fail `_is_generated`, so `sp init --update` — the remedy `doctor` itself prints —
skips them, while `doctor` rewrote them. The marker drift cited as the reason to ignore the
marker is the same drift that made the copilot file read as hand-authored.

Third defect, independent of which authority wins: `_restore()` keeps no copy of what it
replaces, and the warning names only the filename (`doctor.py:299-303`). In a git-tracked
repo that costs a `git restore`; in an untracked one the content is gone.

## 4. What changes in code

### 4.1 The marker check goes; the marker line stays

`_is_generated` has 16 call sites: 15 in `init_project` (`cli_utils.py:1788, 1797, 1806,
1815, 1824, 1833, 1842, 1851, 1860, 1869, 1885, 1901, 1910, 1919, 1928`) and one in
`_configure_copilot` (`cli_utils.py:815`). All 16 go, with `_is_generated` (`:590`) and
`GENERATED_MARKER` (`:587`).

The literal `<!-- Generated by sp init -->` first line stays in the shipped constants, per
the ruling above. Nothing reads it; it warns a human.

### 4.2 `sp init --update` keeps the hello-world step, then delegates

`update=True` reaches exactly three places today:

| today | replaced by |
|---|---|
| the 15 `elif update and _is_generated(...)` branches (`cli_utils.py:1784-1935`) | catalog-driven `_repair_group` in `doctor` |
| `install_global_disciplines(force=update)` / `install_global_skills(force=update)` (`:1938-1939`) | `doctor`'s `~/.sp` group checks — which copy only when diverged rather than unconditionally |
| `_configure_ai_assistants(base_dir, update)` (`:1947`) | the `.cursorrules` / `.windsurfrules` / `.github/copilot-instructions.md` catalog entries |

**The hello-world ruling needs no example-specific code.** "Update if and only if present"
is already `doctor`'s project-scope rule: `_group_check(..., restore_when_absent=False)`
(`doctor.py:384-398`) refreshes a project file when it is present and diverged and never
creates one. `docs/tutorial.md` — part of the same starter set — is already catalogued
`generated` and already behaves that way. So the four example files become four catalog
rows:

```yaml
  - path: prompts/hello.gpt        # and reply.gpt, hello-llmflow.yaml, hello.yaml
    scope: project
    policy: generated
    source: constant
    constant: HELLO_PROMPT
    committed: true
```

If the Captain wants the examples handled by an explicit step in `init_project` *before*
the `doctor` call rather than by catalog rows, that is §5 Q3 below.

`sp init` **without** `--update` keeps its own creation path for a fresh project, gated on
`--no-examples` as now: `doctor` never creates project files, and creating them is `sp
init`'s job (`doctor.py:26-28`).

### 4.3 Shipped text that stops being true

Three constants `sp` writes into every project describe the mechanism being removed:

| site | what it says | after |
|---|---|---|

| `cli_utils.py:726` | CLAUDE.md block — *"generated by `sp init` and refreshed by `sp init --update`"* | incomplete — `sp doctor` refreshes them too |
| `cli_utils.py:1121` | `AI_PROJECT_DOC` — names the four `docs/ai-context/` files as refreshed by `sp init --update` | incomplete, same reason |

### 4.4 `AI_INDEX_DOC` must stop inviting project content

Ruled 2026-08-23 (§5 Q1). The shipped `index.md` keeps `policy: generated`, so anything a
project writes into it is overwritten on the next run of either command. The text must
therefore not invite that writing in the first place — today it does, through open-ended
"Core Documentation" and "External References" sections that read as lists to extend.

Required of the revised `AI_INDEX_DOC` (`cli_utils.py:1153`):

- it says, near the top and unmissably, that this file is `sp`-owned and regenerated, and
  that project-specific pointers belong in `docs/ai-context/project.md` or in documents
  `project.md` points to;
- no section reads as an invitation to add project-specific entries;
- the pointer to `project.md` is prominent rather than one bullet among many.

`project.md` is the file that may name a project's own entry documents — a `HANDOFF.md`
read first every session, design documents with their warnings, a field reference — either
directly or by pointing at a document that lists them.

### 4.5 Not addressed here

`_restore()` keeping no copy of what it overwrites (§2, third defect). Once §5 settles which
files `sp` may overwrite at all, this may not be worth solving; if it is, it is a separate
change and a separate issue.

## 5. Open — six catalog rows

### Q1. `docs/ai-context/index.md`

Today `policy: generated` (`data/file-catalog.yaml:81-86`), which is why discourse-flow's
map was overwritten and will be again on every run.

- **`generated`** — `sp` owns it. A project's own pointers must live in
  `docs/ai-context/project.md`. A fix to the shipped index reaches every project.
- **`create-once`** — written on first `sp init`, never touched again. Each project owns its
  map; `sp` can never correct a stale one.

Two facts pull opposite ways, both checkable:

- `project.md` is already `create-once` (`data/file-catalog.yaml:112-117`) and is the file
  whose stated job is project-owned context, and the shipped `index.md`'s first bullet
  already points at it. On that reading discourse-flow's content was in the wrong file and
  `generated` is consistent with the shipped design.
- But `index.md`'s purpose is navigating *this project's* documents, and the text `sp` ships
  has "Core Documentation" and "External References" sections that invite exactly the
  additions discourse-flow made.

=> IF that is the purpose of index.md, then index.md should be in the project's control, no? What is the argument for keeping it under sp's control?  Or do we need two indexes, one for sp's content and one for project content?  Clear naming and consistency is important here.

**Ruled by the Captain, 2026-08-23** (recorded beneath the slot, not inside it):

> "first point is correct. second point ... yeah, don't invite the external references in
> index.md, make sure it's clear they belong in project.md or files it points to."

So `docs/ai-context/index.md` stays **`policy: generated`** — the first reading holds:
discourse-flow's content was in the wrong file. And the second fact is answered by changing
the shipped text rather than the policy: `AI_INDEX_DOC` must stop inviting project-specific
additions and must say plainly that they belong in `project.md`, or in documents
`project.md` points to. That work is §4.4; the remediation it implies for discourse-flow is
§8.

## 6. Test plan — failing tests first

Written before the code, per rule 15. **`#207` applies: no test may write to the real
`~/.sp`.** `run_doctor` takes `sp_home` and `claude_home` parameters for this; `init_project`
does not, and reaches the real store through `install_global_disciplines` /
`install_global_skills` (`cli_utils.py:1938-1939`), so the delegation test must patch those.

1. **The marker check is gone** — `GENERATED_MARKER` and `_is_generated` are absent from
   `cli_utils`. Guards ruling 3 against reintroduction.
2. **The marker line is retained** — every project-scope `CONSTANT` entry's shipped content
   still begins with `<!-- Generated by sp init -->`. Guards ruling 5.
3. **`sp init --update` delegates** — patch `llmflow.doctor.run_doctor`, call
   `init_project(tmp_path, update=True)`, assert it ran against that project.
4. **The example is refreshed only when present** — a temp project with a modified
   `prompts/hello.gpt` present and `pipelines/hello.yaml` absent: after `--update`,
   `hello.gpt` matches `HELLO_PROMPT` and `hello.yaml` is still absent.
5. **`doctor` writes only catalogued paths** — a temp project holding an uncatalogued file
   with known content is unchanged by a run. Guards ruling 2.
6. **Regression for §2** — its shape depends on Q1 and Q2, so it is named here and written
   once they are ruled.
7. **`tests/test_catalog_covers_init.py`** — its failure message tells a reader to infer
   policy from the `elif update and _is_generated` branch (`:95`), which will no longer
   exist. `AWAITING_CATALOG_RULING` (`:45-54`) empties as Q3–Q6 are ruled.

## 8. Remediation for discourse-flow — hand this to that project

Requested by the Captain, 2026-08-23: *"I need instructions to tell discourse flow how to fix
this correctly on their side now."* Written against that repo's live state — branch `dev`,
52 commits ahead of `origin/dev`, with both damaged files showing as ` M`.

**Why it happened, in one line:** `docs/ai-context/index.md` is a file `sp` owns and
regenerates. Content written into it is destroyed on the next `sp doctor` or
`sp init --update`. The file that survives is `docs/ai-context/project.md`, which `sp`
writes once and never touches again.

**Step 1 — stop, and recover from git.** Do this before running `sp` again in that repo.

```bash
git -C ~/github/nida-institute/discourse-flow restore \
    docs/ai-context/index.md .github/copilot-instructions.md
```

Nothing was committed, so `HEAD` still holds both hand-authored files. If a run has since
overwritten them again, the same command still recovers them.

**Step 2 — keep a copy to work from.**

```bash
git -C ~/github/nida-institute/discourse-flow show HEAD:docs/ai-context/index.md > /tmp/index-was.md
```

**Step 3 — move the content that exists nowhere else into `project.md`.** That repo's
`docs/ai-context/project.md` already opens with a `▶ START HERE — the six live files`
section (line 15), which is where entry-document pointers belong. Three items are unique to
the old index and must be carried over or they are lost for good:

1. `project/HANDOFF.md`, marked *read first, every session*;
2. `project/plans/per-verse-representation-defect-design.md` (#75) **with its warning** —
   *"Read its §0, two ratified decisions were reversed"*;
3. `project/plans/book-discourse-flow-boundary-granularity-design.md` (#75).

Everything else the old index carried — `docs/field-reference.md`,
`docs/translation-usj-reform.md`, `docs/OVERVIEW.md`, and the pipeline, plugin, prompt and
schema directory pointers — is already in that repo's committed `AGENTS.md` under "Where to
find things", so it needs copying only if they want it in both places. Verify that before
relying on it.

**Step 4 — let `index.md` go back to the packaged text.** Once `project.md` carries the
three items, discard the local `index.md` changes and let `sp` own the file:

```bash
git -C ~/github/nida-institute/discourse-flow checkout -- docs/ai-context/index.md   # or run sp doctor
```

**Step 5 — `.github/copilot-instructions.md`.** Its policy is **not yet ruled** (§5 Q2), so
`sp` may or may not keep overwriting it. Migrating is the safe move either way: the 72 lines
recovered in step 1 — the pipeline name, the `--var book=` values, the `--rewind-to
prepare_synthesis_input` recipe, the `output/intermediate/` warning, and the
AI-authority-boundaries section — belong in `project.md` or in a document `project.md`
points at. Content there survives regardless of how Q2 lands.

**Step 6 — verify.** Run `sp doctor`, then check the tree:

```bash
git -C ~/github/nida-institute/discourse-flow status --short
```

Only files that repo owns should appear. If `docs/ai-context/index.md` shows as modified,
`sp` and the repo still disagree about who owns it and the migration is incomplete.

**The general rule for that project, and any consumer repo:** anything a human or an agent
authors goes in `docs/ai-context/project.md` or in a document it points to. The four files
`sp` generates — `index.md`, `overview.md`, `rules.md`, `github-workflow.md` — are not
places to write.

## 9. What will not change

- **`CLAUDE.md`** — user-owned, and a missing one is INFO not a failure (D3-A,
  `doctor.py:30-34`).
- **`docs/ai-context/project.md`** — `create-once`; the one file a project is invited to own
  (`doctor.py:35-37`).
- **`~/.sp/user-context/`** — not catalogued and not checked (D6, `file_catalog.py:15-17`).
- **`~/.sp` restore semantics** — a file there is restored when missing *or* diverged; only
  the project-scope rule is "present and diverged".
- **`sp init`'s creation path** for a fresh project, including `--no-examples`.
- **`docs/ai-context/` in this repository** — generated by `tools/update_ai_context.py`, a
  different mechanism, and never written by an AI session (rule 15, CLAUDE.md).
- **The discourse-flow working tree** — the recovery in §2 is the Captain's to run.
